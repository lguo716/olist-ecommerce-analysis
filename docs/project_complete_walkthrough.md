## 1. 先理解：这个项目究竟在做什么

你扮演电商平台数据分析师，用 Olist 2016—2018 年的订单记录回答四件事：

1. 经营规模是否增长，增长来自订单量还是客单价？
2. 顾客有没有再次购买，哪些顾客适合维护和召回？
3. 物流履约和顾客评分之间有什么关系？
4. 问题集中在哪些收货地区、品类和商家？

整个项目的顺序是：

```text
业务问题 → 九张原始表 → 数据质量检查 → 一单一行订单模型
→ 经营指标 → 用户复购与RFM → 同期群留存
→ 物流和评分 → 州/品类/商家诊断 → Power BI → 结论与行动建议
```

每一步都要解释三个问题：输入是什么、怎样计算、怎样核对。

## 3. 第一阶段：把业务问题对应到数据

### 目的

明确“要分析什么”，认识表粒度。粒度就是一行究竟代表什么。

| 原始表 | 一行代表什么 | 主要用途 |
|---|---|---|
| orders | 一笔订单 | 订单状态、下单和配送时间 |
| order_items | 一笔订单的一个商品行 | 商品金额、运费、品类和商家 |
| order_payments | 一笔订单的一条支付记录 | 支付金额、方式、分期 |
| order_reviews | 一条评价记录 | 评分和评论 |
| customers | 一条订单使用的顾客身份/地址记录 | 稳定顾客标识、城市、州 |
| products | 一种商品 | 品类、重量、尺寸 |
| sellers | 一名商家 | 商家身份和地址 |
| geolocation | 一条邮编位置记录 | 经纬度；同一邮编可能有多行 |
| category translation | 一个品类的名称翻译 | 葡萄牙语品类转英文 |

`orders`是订单表，不是所有表的总目录。`order_id`是订单业务键，用来识别订单和匹配相关记录。

`customer_id`用于连接orders和customers；`customer_unique_id`用于识别跨订单的同一个人。

本项目州级分析直接使用收货州，不需要经纬度；geolocation验证文件完整性，但不加载进主要分析流程。

## 4. 第二阶段：数据质量检查

### 目的

在计算指标之前判断数据能否支持分析。

### 操作顺序

1. 检查九张CSV、必需字段、行列数、文件大小和SHA256指纹。
2. 按业务键检查重复：订单用order_id，商品行用order_id + order_item_id，支付用order_id + payment_sequential，评价用review_id + order_id。
3. 检查缺失字段，区分“未填写”与“无法完成分析”。
4. 检查孤儿记录：例如商品行order_id在订单表找不到对应订单。
5. 检查价格、运费、支付金额及评分范围。
6. 检查时间先后顺序，并明确异常影响哪些分析。

质量规则分为：ERROR必须解决；WARN记录并排除受影响的分析；INFO提示口径。

例如交给承运商早于下单有166笔，收货早于交运有23笔。它们仍可支持订单量或商品金额统计；分析涉及这些异常承运时间的时长时才排除。本项目“实际收货减下单”和“实际减预计收货”不使用承运时间。

评价标题或评论缺失不删除评分；缺失品类标记unknown并保留金额；缺失商品尺寸只影响尺寸分析。原始CSV不直接删除或修改。

输出：`reports/tables/data_quality_summary.csv`、`data_quality_checks.csv`。

学习入口：[第二阶段文档](learning_stage_02_data_quality.md)，脚本`src/inspect_data_quality.py`。

## 5. 第三阶段：建立一单一行的分析模型

### 目的

把订单需要的金额、支付、评分和顾客信息整理到一行，避免金额重复。

### 为什么不能直接连接明细

同一订单有2个商品行、2条支付、2条评价时，用order_id直接连接三张明细会产生2×2×2=8个组合。每个商品价格会出现4次，再求和就放大4倍。

连接的意思是：用两个表中的相同键，给左表记录补充右表字段，不是把CSV上下堆在一起。

### 正确处理

```text
order_items → 按order_id分组 → 商品金额、运费、件数、商家数
payments    → 按order_id分组 → 支付金额、记录数、最大分期、主要支付方式
reviews     → 按order_id分组 → 平均评分、评价数、是否有评论

orders → 按customer_id连接customers
       → 按order_id连接上述三张聚合表
       → 最终每个order_id只出现一次
```

例如某订单商品价格100和50，先SUM得到150；支付120和50，先SUM得到170；评分5和3，先AVG得到4。连接后这笔订单只有一行，商品金额150、支付金额170、订单级评分4。

Python实现对应`build_order_model()`：`groupby().agg()`聚合，`merge()`连接；`validate="one_to_one"`检查聚合后的关系是否一对一。

新增字段包括purchase_date、purchase_month、is_delivered、delivery_days、delivery_delta_days和is_late。一个订单多条评分取平均，因此订单级评分可能是小数，Power BI不能把它强制转为整数。

验收：订单模型99,441行，order_id唯一，商品金额聚合前后守恒。

输出：`data/processed/powerbi_orders.csv`。商品明细和顾客底表分别保留在另外两个CSV中，不能把所有分析都硬塞进订单表。

学习入口：[第三阶段文档](learning_stage_03_order_model.md)，脚本`src/inspect_order_model.py`。

## 7. 第五阶段：用户复购与RFM

### 目的

识别再次购买的人，并形成可维护、可召回的顾客分层。

### 总体复购

只使用delivered订单，按customer_unique_id统计订单数。至少2单是复购顾客：2,801 ÷ 93,358 = 3.00%。这是整个数据窗口内的复购率。

### 90天复购

把每位顾客的订单按购买时间排序，取得首单和第二单。参考日期为2018-08-30：

```text
观察天数 = 参考日期 - 首购日期
可观察顾客 = 观察天数至少90天
90天复购 = 可观察顾客的第二次购买发生在首购后0至90天内
```

75,563人可观察，17,795人观察期不足；1,718人90天内复购，1,718 ÷ 75,563 = 2.27%。晚首购顾客不能因为数据提前结束就被判为“没有复购”。

### RFM

R是最近购买距参考日的天数，F是成交订单数，M是累计成交商品金额。不是距今天的天数。

分层按代码中顺序匹配：

| 分层 | 判断规则 | 人数 |
|---|---|---:|
| Champions 核心顾客 | F≥3且R≤90 | 59 |
| Loyal 忠诚顾客 | 未进入上组，F≥2且R≤180 | 1,171 |
| At-risk repeat 流失风险复购客 | 其余F≥2 | 1,571 |
| High-value new 高价值新客 | 其余R≤90且M评分≥4 | 7,001 |
| New 新客 | 其余R≤90 | 10,778 |
| Hibernating 沉睡顾客 | 其余R>365 | 20,310 |
| Need attention 待关注顾客 | 其余顾客 | 52,468 |

R、M评分使用五分位；F高度集中在1单，因此按明确次数打分，不用分位数随意拆开同频次顾客。

首单准时顾客90天复购率2.29%，延迟2.06%。首单金额分组虽然p≈0.000072，Cramér's V≈0.018，实际差异很小，不宜把金额分组显著性当成大的运营提升机会。

验收：顾客底表唯一；RFM覆盖93,358人；RFM金额等于平台GMV；90天样本观察天数与第二单时间正确。

学习入口：[第五阶段文档](learning_stage_05_customer_repurchase.md)，脚本`src/inspect_customer_repurchase.py`。

## 8. 第六阶段：同期群留存

### 目的

比较不同首购月份的人，在之后每一个自然月有没有再次购买。

1. 订单日期转为自然月activity_month。
2. 每位顾客最早的购买月作为cohort_month。
3. 同一顾客同一月多单，只记1名活跃顾客。
4. cohort_index = 活动月与首购月的月份差。
5. 每组每月活跃人数 ÷ 该组首购人数，得到留存率。

例如某顾客2017-01首购，2017-03买两次：他属于2017-01同期群，在第0月贡献1人、第2月贡献1人，不是第2月贡献2人。如果该同期群有100人，第2月10人购买，留存率就是10%。

这是“当月复购留存”，不是累计留存。已到达但没人复购的月份记0%；尚未到达的月份留空。第0月都为100%。

数据保留23个同期群，覆盖93,358名顾客；看板主要展示20个完整核心首购月份。加权第1月为421 ÷ 87,214 = 0.4827%，第2月为273 ÷ 81,265 = 0.3360%，不能直接平均不同大小同期群的百分比。

输出：`cohort_retention_tidy.csv`长表、`cohort_retention_matrix.csv`矩阵、静态热力图及Power BI热力矩阵。

学习入口：[第六阶段文档](learning_stage_06_cohort_retention.md)，脚本`src/inspect_cohort_retention.py`。

## 9. 第七阶段：物流履约与用户评分

### 目的

比较准时和延迟订单的评分差异，以及这种差异的业务幅度。

从96,478笔成交订单筛选出同时有实际/预计配送时间和评分的95,824笔订单：

```text
delivery_days = 实际收货时间 - 下单时间
delivery_delta_days = 实际收货时间 - 预计收货时间
delivery_delta_days > 0 → 延迟；否则准时
订单级平均评分≤2 → 低评分
```

| 指标 | 准时 | 延迟 |
|---|---:|---:|
| 分析订单 | 88,163 | 7,661 |
| 平均评分 | 4.29 | 2.57 |
| 低评分订单 | 8,100 | 4,136 |
| 低评分率 | 9.19% | 53.99% |
| 平均履约天数 | 10.88 | 31.38 |

低评分率相差44.80个百分点，风险比约5.88倍，平均评分相差-1.7278分。

Welch 95%置信区间[-1.7657,-1.6899]描述均值差异；Mann–Whitney U比较评分分布；Spearman=-0.1757描述配送偏差天数和评分的单调关系。两项检验p<1e-300。

分组差异大但Spearman仅弱负相关并不矛盾：前者关注是否越过预计日期，后者使用全部天数排序。结果支持优先调查物流体验，不把观察性对比当成已实施干预的因果效果。

输出：`delivery_review_summary.csv`、`statistical_tests.csv`及配送评分对比图。

学习入口：[第七阶段文档](learning_stage_07_delivery_satisfaction.md)，脚本`src/inspect_delivery_satisfaction.py`。

### 目的

品类金额使用商品行price；先聚合到“订单+品类”再统计评分。商家先聚合到“订单+商家”；州直接使用订单模型的customer_state。

## 11. 第九阶段：四页Power BI经营看板

### 模型和关系

导入11张已整理CSV，新增Date日期表和Metrics度量表。只保留三条单向关系：

```text
Date[Date] 1 → * powerbi_orders[purchase_date]
powerbi_customers[customer_unique_id] 1 → * powerbi_orders[customer_unique_id]
powerbi_orders[order_id] 1 → * powerbi_order_items[order_id]
```

月度、同期群、品类、商家、州和首单体验汇总表保持独立。它们已经按自己的口径汇总，不能自动建立多对多关系传播日期筛选。

Date标记为日期表，Year Month按Year Month Sort排序。文本ID不求和；时间和金额类型正确；is_late缺失保留空值。

Metrics是组织DAX度量的表；不使用被Power BI保留的表名Measures。

### DAX重点

COUNT/DISTINCTCOUNT计数，SUM求金额，DIVIDE求比率，CALCULATE控制筛选上下文。

购买顾客和复购顾客从当前订单筛选内重新统计，不能直接用顾客历史frequency判断某个月复购。KEEPFILTERS让成交条件与订单状态筛选取交集，选canceled时不会仍显示全部成交GMV。

准时计数必须排除空白is_late，因为DAX的普通等号可能把空白视为FALSE。低评分必须排除空白评分。GMV环比不在总计或边界月显示无意义结果。

### 四页怎样读

1. **经营总览**：六张KPI卡、月度组合图、Top10品类、州/城市矩阵和月份/州/状态筛选。点击州矩阵的“+”展开城市；列表较长时滚动查看。
2. **用户与复购**：完整历史总体复购、固定90天观察指标、RFM、频次、同期群、月度新客/复购客、首单体验。不要给固定90天口径套首页日期筛选。
3. **物流与满意度**：准时率、履约天数、评分、低评分率；准时蓝、延迟红；州和商家关注清单。
4. **品类与商家**：规模/质量矩阵、同期增长与评分变化、商家成交额/评分象限、商品重量/体积和运费散点。

首页默认2017-01至2018-08，因此卡片GMV为13,181,027.13 BRL、成交订单96,211、购买顾客93,104。全窗口GMV为13,221,498.11 BRL、成交订单96,478、购买顾客93,358。核对全窗口时，清除首页的完整月份页面筛选与三个切片器；两套数字不能混用。

页面中的静态解读、独立诊断汇总表标注历史全窗口，不随所有明细筛选变化；动态KPI和明细趋势才按所选窗口重算。分析时先读页面副标题和范围。

交付：`powerbi/olist_ecommerce_analysis.pbix`；可编辑源项目`powerbi/Olist.pbip`及配套Report、SemanticModel目录；四张截图位于`reports/figures/powerbi_0*.png`。

学习入口：[第九阶段文档](learning_stage_09_powerbi_dashboard.md)、[逐步搭建清单](../powerbi/build_checklist.md)。
