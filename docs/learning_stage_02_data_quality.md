# 学习阶段 2：数据质量检查

这一阶段先不计算GMV、复购率，也不制作看板。目标是确认原始数据是否完整、结构是否正确、表之间能否关联，以及哪些异常会影响后续分析。

## 1. 本阶段整体要做什么

数据质量检查不是简单地“找到空值并删除”，而是依次回答：

```text
文件是否齐全
→ 字段是否正确
→ 一行能否被唯一识别
→ 表与表能否正确关联
→ 金额和评分是否在合理范围
→ 时间顺序是否符合业务过程
→ 异常应该阻断、警告还是只做提示
```

如果跳过这一步，后续可能出现订单重复、金额放大、顾客无法识别、配送时长为负数等问题。

## 4. 文件与字段完整性

第一层检查确认九张CSV全部存在，并包含分析所需字段。

Python中的核心逻辑是：

```python
missing = [filename for filename in FILES.values() if not (RAW_DIR / filename).exists()]
absent = expected_columns.difference(actual_columns)
```

同时记录：

- 行数和列数；
- 文件大小；
- SHA256文件指纹；
- 字段检查结果。

SHA256可以理解为文件的“数字指纹”。只要文件内容发生变化，指纹通常就会变化，因此可以用来确认团队成员使用的是同一版本数据。

当前结果：九张CSV均存在，必需字段全部通过。

## 5. 完整重复与业务键重复

完整重复表示一整行所有字段都相同；业务键重复表示本应唯一识别一行的字段组合重复。

```python
frame.duplicated().sum()
frame.duplicated(["order_id", "order_item_id"]).sum()
```

主要业务键为：

| 表 | 业务键 |
|---|---|
| 订单 | `order_id` |
| 顾客 | `customer_id` |
| 商品明细 | `order_id + order_item_id` |
| 支付 | `order_id + payment_sequential` |
| 评价 | `review_id + order_id` |
| 商品 | `product_id` |
| 商家 | `seller_id` |

当前已加载表的完整重复和业务键重复均为0。评价表中的`review_id`单独不唯一，因此必须检查组合业务键。

## 6. 缺失值不能统一处理

Python使用：

```python
frame.isna().sum()
```

但真正重要的是解释缺失产生的业务原因。

| 缺失字段 | 缺失数量 | 处理原则 |
|---|---:|---|
| 评价标题 | 87,656 | 顾客没有填写文字，不删除评分 |
| 评价正文 | 58,247 | 顾客没有填写文字，不删除评分 |
| 商品品类及文字属性 | 610 | 保留金额，品类标记为`unknown` |
| 商品重量和长宽高 | 各2 | 保留交易，只从重量或体积分析中排除 |
| 订单批准时间 | 160 | 结合订单状态判断，不统一填补 |
| 交给承运商时间 | 1,783 | 多数订单尚未进入配送流程 |
| 实际送达时间 | 2,965 | 多数订单被取消、不可用、未送达或仍在处理中 |

因此：

```text
缺失值 ≠ 错误值
没有评价正文 ≠ 没有评分
尚未送达 ≠ 送达时间为0
```

## 7. 表关系完整性与孤儿记录

孤儿记录是指明细表中存在外键值，但对应的主表记录不存在。

例如，商品明细中出现订单编号，但订单表找不到该订单：

```sql
SELECT COUNT(*)
FROM order_items i
LEFT JOIN olist_orders o
    ON o.order_id = i.order_id
WHERE o.order_id IS NULL;
```

这里必须使用`LEFT JOIN`：先保留所有商品行，再筛选没有匹配到订单的记录。

本项目检查六类孤儿关系：

- 订单找不到顾客；
- 商品行找不到订单；
- 商品行找不到商品；
- 商品行找不到商家；
- 支付找不到订单；
- 评价找不到订单。

当前六项结果全部为0。

## 9. 时间顺序检查

正常订单流程应当是：

```text
下单 → 批准/付款确认 → 交给承运商 → 顾客收货
```

当前结果：

| 检查 | 异常行数 | 处理 |
|---|---:|---|
| 批准早于下单 | 0 | 通过 |
| 交给承运商早于下单 | 166 | 记录为警告，不用于相关时长分析 |
| 顾客收货早于交给承运商 | 23 | 记录为警告，不用于相关时长分析 |
| 顾客收货早于下单 | 0 | 通过 |

这些记录不会从原始CSV删除，因为其他字段仍可能支持订单量或金额分析。只在使用异常时间字段的分析中排除。

样本首月2016-09和末月2018-10也可能是不完整月份。因此核心趋势比较使用2017-01至2018-08，避免把不完整月份误判为业务下降。

## 10. ERROR、WARN和INFO

| 等级 | 含义 | 当前处理 |
|---|---|---|
| `ERROR` | 会破坏核心关系或指标 | 必须解决后才能继续 |
| `WARN` | 只影响局部字段或专项分析 | 保留记录，排除受影响用途 |
| `INFO` | 不是错误，只提醒口径 | 在报告和图表中说明 |

自动化测试只允许`ERROR`级检查全部为0：

```python
blocking = checks[checks["severity"].eq("ERROR")]
self.assertTrue(blocking["failed_rows"].eq(0).all())
```

当前没有阻断级错误，可以进入下一阶段的订单模型构建。
